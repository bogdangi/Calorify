📝 User Story: Accessibility, Error Handling & Performance Polish

Title: Accessibility & Polish
Feature: Accessible UI, graceful error handling everywhere, mobile performance
User Story:
• As any user (assistive technology, unreliable browser, slow device),
• I want the app usable, resilient, and fast,
• So that nothing in the environment prevents me from tracking my food.

Status: 🚧 Partial — error handling + approximate labeling exist in `PhotoCaptureModal.tsx`; dedicated accessibility pass, Web Worker inference, and dev perf metrics are not yet visible in the code.

⚙️ Acceptance Criteria

1. Accessibility: semantic HTML, keyboard accessibility, accessible labels, sufficient touch targets, screen-reader-friendly controls, translated accessibility text, visible focus states, proper dialog behavior.
2. Error handling (graceful, always with manual fallback): camera unavailable, permission denied, unsupported browser, ML model loading failure, ML inference failure, invalid imported JSON (→ US-13), IndexedDB errors (→ US-2), offline state (→ US-12), insufficient model confidence.
3. Performance: lazy-load ML code and models, avoid unnecessary React renders, efficient IndexedDB usage, reasonable bundle size, avoid blocking the main thread, WebGPU when available with WASM fallback, progress during model load/inference, expensive ML inference in a Web Worker where practical, inference time measured only in dev/debug.
